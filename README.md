# ML-Enabled IoT-Based Rubber Plantation Monitoring and Tapping Decision System

An ESP32-based IoT system that monitors rubber plantation conditions (temperature, humidity, soil moisture, rain, flame), uploads readings to ThingSpeak, and uses a Random Forest model served through a FastAPI backend to predict whether current conditions are suitable for rubber tapping. SMS alerts are sent through Twilio, and an independent fire-safety subsystem drives a buzzer and water pump.

> **Prototype status:** the ML model is trained on a **synthetic dataset**. Reported metrics validate the software pipeline only and **do not represent real-world tapping accuracy**. See [Limitations](#limitations-and-known-issues).

## Features

- **Environmental monitoring:** DHT11 (temperature and humidity), analog soil moisture, and digital rain detection.
- **Cloud logging:** temperature, humidity and soil moisture are pushed to ThingSpeak for charts and history.
- **ML tapping decision:** the ESP32 posts readings to a FastAPI `/predict` endpoint and receives `Suitable` / `Not Suitable` with a probability.
- **SMS notifications:** the backend sends Twilio SMS alerts, so credentials never live on the microcontroller.
- **Independent fire response:** flame detection triggers the buzzer and pump locally, with no dependency on Wi-Fi, the backend or the ML model.
- **Resilient firmware:** non-blocking timers, Wi-Fi auto-reconnect and DHT read validation.

## System Architecture

```
Sensors (DHT11 · Soil · Rain · Flame)
              │
              ▼
           ESP32 ───────────── Flame → Buzzer + Relay → Pump   (local, independent)
              │ Wi-Fi
     ┌────────┴─────────┐
     ▼                  ▼
 ThingSpeak       FastAPI backend
 (storage &             │
  charts)        Random Forest model
                        │
                        ▼
              Suitable / Not Suitable
                        │
                        ▼
                  Twilio SMS
```

| Layer | Technology |
|---|---|
| Microcontroller | ESP32 (Arduino IDE, C/C++) |
| Cloud IoT | ThingSpeak |
| ML | Python, Pandas, NumPy, scikit-learn (Random Forest), Joblib |
| API | FastAPI + Uvicorn |
| Notifications | Twilio SMS |

## Hardware

| Component | Purpose |
|---|---|
| ESP32 | Controller and Wi-Fi |
| DHT11 | Temperature and humidity |
| Soil moisture sensor | Soil moisture (analog) |
| Rain sensor | Rain / no rain (digital) |
| Flame sensor | Fire detection (digital) |
| Buzzer | Audible fire alarm |
| 2-channel 5V relay | Switches the pump |
| Mini DC water pump | Fire suppression |
| 5V supply, jumper wires, breadboard/PCB | Power and assembly |

### Pin mapping

| Device | ESP32 GPIO | Interface |
|---|---|---|
| DHT11 data | 27 | Single-wire digital |
| Soil moisture | 32 | Analog (ADC) |
| Rain sensor | 5 | Digital input |
| Flame sensor | 22 | Digital input |
| Buzzer | 21 | Digital output |
| Relay IN | 33 | Digital output |

No I²C or SPI is required.

> **Power note:** never power the pump directly from an ESP32 GPIO. Switch it through the relay with a suitable supply.

## Getting Started

### 1. Train the ML model

Requirements: Python 3.9+ and Jupyter.

```bash
pip install numpy pandas matplotlib scikit-learn joblib jupyter
jupyter notebook ml/rubber_plantation_ml.ipynb
```

Run all cells from the **project root** as the working directory (for example, start Jupyter from the root). The notebook will:

1. Generate a 5,000-sample synthetic dataset and save it to `data/rubber_sensor_data.csv`
2. Preprocess it and do an 80/20 stratified train/test split
3. Train a Random Forest (`n_estimators=200`, `random_state=42`) and print metrics
4. Save the model to `ml/tapping_model.pkl`
5. Write `backend/app.py`, `backend/notifications.py` and `backend/requirements.txt`

### 2. Run the backend

```bash
cd backend
pip install -r requirements.txt
```

Set Twilio credentials and the alert recipient as environment variables. If the Twilio variables are missing, the backend prints the SMS to the console instead of sending it, which is useful for testing.

```bash
export TWILIO_ACCOUNT_SID="ACxxxxxxxxxxxxxxxx"
export TWILIO_AUTH_TOKEN="your_auth_token"
export TWILIO_FROM_NUMBER="+1XXXXXXXXXX"
export ALERT_PHONE_NUMBER="+91XXXXXXXXXX"
# Optional; defaults to ../ml/tapping_model.pkl (run from backend/)
export MODEL_PATH="../ml/tapping_model.pkl"
```

Start the server:

```bash
uvicorn app:app --host 0.0.0.0 --port 8000
```

Test it:

```bash
curl http://localhost:8000/health

curl -X POST http://localhost:8000/predict \
  -H "Content-Type: application/json" \
  -d '{"temperature": 29.4, "humidity": 83, "soil_moisture": 48, "rain": 0}'
```

The ESP32 must be able to reach the backend over your network. Use the server's LAN IP or a public HTTPS domain, not `localhost`.

### 3. Flash the ESP32

1. Install the **ESP32 board package** in the Arduino IDE.
2. Install these libraries via Library Manager:
   - **DHT sensor library** (Adafruit)
   - **Adafruit Unified Sensor**
   - **ArduinoJson** (Benoit Blanchon)
3. Open `esp32/rubber_monitoring.ino` and edit the user configuration block:

   ```cpp
   const char* WIFI_SSID                = "YOUR_WIFI_SSID";
   const char* WIFI_PASSWORD            = "YOUR_WIFI_PASSWORD";
   const char* THINGSPEAK_WRITE_API_KEY = "YOUR_THINGSPEAK_WRITE_API_KEY";
   const char* BACKEND_HOST             = "http://YOUR_BACKEND_HOST:8000";
   ```

4. Adjust the sensor logic levels and soil calibration if needed (see [Configuration Reference](#configuration-reference)).
5. Select your ESP32 board, upload, and open the Serial Monitor at **115200 baud**.

### 4. Set up ThingSpeak

Create a channel with three fields and copy its **Write API Key** into the firmware:

| Field | Data |
|---|---|
| Field 1 | Temperature (°C) |
| Field 2 | Humidity (%) |
| Field 3 | Soil moisture (%) |

## API Reference

### `GET /health`

```json
{ "status": "ok" }
```

### `POST /predict`

Request:

```json
{ "temperature": 29.4, "humidity": 83, "soil_moisture": 48, "rain": 0 }
```

Response:

```json
{ "prediction": "Suitable", "probability": 0.96 }
```

`prediction` is `"Suitable"` or `"Not Suitable"`. `probability` is the model's predicted probability of the *Suitable* class. When the result is *Not Suitable*, the backend also sends an SMS through Twilio.

### `POST /fire-alert`

Called by the ESP32 when the flame sensor triggers.

Request:

```json
{ "event": "flame_detected", "message": "FIRE ALERT: Flame detected in plantation. Pump activated." }
```

Response:

```json
{ "status": "alert_sent", "event": "flame_detected" }
```

## ML Model

**Features:** `temperature`, `humidity`, `soil_moisture`, `rain`
**Target:** `suitable` (0 = Not Suitable, 1 = Suitable)

**Synthetic data:** feature ranges are temperature 18–40 °C, humidity 40–100 %, soil moisture 5–95 %, rain 0/1. Labels come from a nonlinear suitability score, using Gaussian-shaped preferences around roughly 27 °C, 82 % humidity and 45 % soil moisture minus a rain penalty. The score is converted to a probability and labels are sampled from it, so the classes overlap and the model has real work to do.

**Latest notebook run (synthetic test set, 1,000 samples):**

| Metric | Value |
|---|---|
| Accuracy | 79.40% |
| Precision | 77.85% |
| Recall | 77.17% |
| F1-score | 77.51% |

The final project report lists 75.10% accuracy from an earlier prototype run. Figures differ slightly between runs because of the generation and sampling setup, and both are synthetic-data results only. Feature importances also vary from run to run for the same reason.

## Fire Safety Subsystem

Fire handling runs on **every loop iteration** on the ESP32 and is deliberately independent of Wi-Fi, the backend and the ML model.

| Condition | Action |
|---|---|
| Flame detected (rising edge) | Buzzer ON, relay ON (pump ON), best-effort `POST /fire-alert` |
| Flame cleared (falling edge) | Buzzer OFF, relay OFF (pump OFF) |

The SMS is rate-limited by `FIRE_SMS_COOLDOWN` (60 s) and never delays the local suppression response.

## Configuration Reference

**Timing** (`rubber_monitoring.ino`):

| Constant | Default | Meaning |
|---|---|---|
| `SENSOR_READ_INTERVAL` | 5 s | Sensor read cycle |
| `THINGSPEAK_INTERVAL` | 20 s | ThingSpeak upload (free tier needs ≥15 s) |
| `PREDICTION_INTERVAL` | 30 s | Prediction request to backend |
| `FIRE_SMS_COOLDOWN` | 60 s | Minimum gap between fire SMS requests |

**Sensor logic levels:** many rain and flame modules output `LOW` when triggered, and relay modules differ in active level. Adjust these to match your hardware:

```cpp
#define RAIN_DETECTED_LEVEL   LOW
#define FLAME_DETECTED_LEVEL  LOW
#define RELAY_ON_LEVEL        HIGH
#define RELAY_OFF_LEVEL       LOW
```

**Soil calibration:** the ESP32 ADC is 12-bit (0–4095). Measure the raw reading with the sensor in dry air and in water, then set:

```cpp
#define SOIL_ADC_AIR_VALUE    3300   // 0 % moisture
#define SOIL_ADC_WATER_VALUE  1200   // 100 % moisture
```

**Backend environment variables:** `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_FROM_NUMBER`, `ALERT_PHONE_NUMBER`, `MODEL_PATH`.

## Limitations and Known Issues

**Scientific**
- The model is trained on synthetic data. Field accuracy is unknown until it is retrained on real sensor readings paired with actual tapping outcomes and latex yield.
- Real tapping suitability depends on biological and operational factors not captured by the four current features.

**Hardware**
- The DHT11 has limited accuracy. The soil sensor needs calibration per soil type. Resistive rain sensors degrade with contamination. One sensor node cannot represent an entire plantation.

**Software (worth addressing before deployment)**
- **SMS spam:** `/predict` sends an SMS on *every* `Not Suitable` result, and the ESP32 requests predictions every 30 s. Add a cooldown or send only on state changes.
- **Plain HTTP and secrets:** the firmware talks to ThingSpeak and the backend over HTTP, with the ThingSpeak key in the URL and no authentication on the backend. Use HTTPS and an API key or token for production.
- **Hard-coded credentials:** Wi-Fi and ThingSpeak keys are in the sketch. Keep them out of version control.
- **Backend paths:** `app.py` loads the model from `../ml/tapping_model.pkl`, so start it from inside `backend/` or set `MODEL_PATH`.
- **Deprecated call:** `app.py` uses `data.dict()`, which is deprecated in Pydantic v2. Use `data.model_dump()` if you see a warning.
- **Fire alert recipient:** fire alerts reuse `ALERT_PHONE_NUMBER`, the same recipient as tapping alerts.
- **Pump runtime:** the pump stays on while the flame sensor reads active, with no maximum run-time cutoff. Consider adding a dry-run or timeout safeguard.

## Roadmap

- Collect field data: timestamped sensor readings, whether tapping was performed, and latex yield/quality.
- Retrain the model on field data and re-evaluate against real outcomes.
- Add rate limiting and de-duplication for SMS notifications.
- Move to HTTPS with authenticated endpoints.
- Upgrade sensors (for example a more accurate temperature/humidity sensor) and add multiple sensor nodes across the plantation.
- Add a small dashboard or mobile view for predictions alongside ThingSpeak.
